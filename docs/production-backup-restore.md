# Household backup and recovery

This is an operator procedure. It uses a direct PostgreSQL connection as `postgres`, never an app session or Function response. The operator's database credential, 32-byte archive key, encrypted archive, and invite links are secrets. Limit access to named operators and record the operator name in `BACKUP_OPERATOR`.

## Weekly export

1. In the approved secret manager, generate and retain a random 32-byte archive key. Set `BACKUP_KEY_HEX` to its 64-character hex value for the command. Store the key separately from the archive; test retrieval. Set `DATABASE_URL` to the production direct PostgreSQL URL (TLS required) and `BACKUP_OPERATOR` to the named operator. Do not put values in shell history or the repository.
2. At least once every seven days, run `npx tsx scripts/household-backup.ts export HOUSEHOLD_ID OUTPUT_DIR` for each production household. The output directory must not exist. The command reads one repeatable-read database snapshot, writes encrypted 100-record NDJSON chunks and an encrypted versioned manifest, then logs a **local export** audit row. The manifest records source household and revision, per-kind counts, chunk counts/bytes/SHA-256, effort contributions, and email/role recovery map. No old user IDs are exported. Record the printed export digest.
3. Copy the complete directory to approved encrypted offsite storage. Confirm that storage reports a durable copy and restricts access to recovery operators. Retrieve or mount that offsite copy at a separate path, then run `npx tsx scripts/household-backup.ts verify COPIED_ARCHIVE_DIR EXPORT_DIGEST OFFSITE_LOCATION`, where `OFFSITE_LOCATION` is the durable storage object or directory identifier. The command decrypts and validates every copied chunk, compares the digest with the original export digest and local export audit, then appends a distinct `verified-copy` audit row containing that location. The local export row alone is not backup success. Delete the local export directory after the verified-copy row is present. Keep several weekly generations under the organization's retention policy. A weekly backup is complete only after verified-copy audit; if it fails, retry within seven days or the one-week recovery point is no longer met.
4. Monthly, rehearse decryption and restore into an isolated local Supabase project with a disposable key and household. Record archive digest, restore counts, and recovery checks. Never rehearse against production.

The local CLI encrypts each file with AES-256-GCM using a fresh random nonce. The key is not in the archive; losing it makes recovery impossible. Offsite access controls and key custody must be configured by the operator before relying on this procedure.

## Recovery

1. Retrieve one complete archive directory and its key through the approved channels. Compare the expected archive digest from the export log to the digest the CLI reports. Confirm the intended source household and revision. Preserve the source and archive throughout recovery.
2. Set `DATABASE_URL`, `BACKUP_KEY_HEX`, and `BACKUP_OPERATOR` for the destination. Run `npx tsx scripts/household-backup.ts restore ARCHIVE_DIR new`. To use an existing household, pass its UUID only after confirming it has revision zero and no records, memberships, or invitations. The CLI rejects a nonempty target. It validates encrypted chunks, hashes, counts, record schemas and cross-record/history links, then stages in 100-row batches that users cannot read. A crashed stage may be restarted only with the matching archive digest; the CLI clears that matching stage and reloads it. On ordinary failure it clears the stage. Publication copies records, refs, unavailable lines and effort contributions/totals and sets the source revision in one transaction. No user has access until a later bind.
3. Compare the published record count, revision, refs, unavailable lines, effort totals, and audit rows to the source manifest and expected application behavior. Keep the household closed to users until this check passes.
4. Have the recovered creator sign in through the destination auth system and freshly verify the email address from the archive's creator recovery entry. Resolve the new `auth.users.id` from the verified account. Run `npx tsx scripts/household-backup.ts bind ARCHIVE_DIR RESTORED_HOUSEHOLD_ID VERIFIED_USER_ID`. The database checks current verified email and empty membership/invitation state before binding the creator. The source user ID grants no authority.
5. For each recovered member, run `npx tsx scripts/household-backup.ts invite ARCHIVE_DIR RESTORED_HOUSEHOLD_ID MEMBER_EMAIL HTTPS_APP_URL`. Deliver each fresh 24-hour, email-bound invite through the approved channel. The CLI accepts only member emails in the encrypted recovery map and requires a bound creator. Do not reuse old invitation tokens.

The `postgres` credential can change any database data, so it must be controlled as an operator credential. The audit table is append-only during normal database operations and records local export, verified copy, stage, publish, bind, and invite actions, including operator name, archive digest, and offsite location where applicable. Review it after every operation. This procedure does not copy the archive offsite automatically and does not send invite links.
