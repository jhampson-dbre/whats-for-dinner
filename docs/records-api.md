# Household records API

`/api/records` requires a bearer access token for a verified, nonanonymous Supabase user. Every page and write, including an idempotent replay, checks current household membership inside its database transaction. The service key stays on the server. The tables and RPCs are denied to `anon` and `authenticated` and granted to `service_role`.

## Records

The kinds are `settings` (one record with ID `settings`), `meal`, `recipe`, `plan`, `slot`, `shopping-item`, `repair`, `outcome`, and `leftover-lot`. Values use the V4 shapes in `src/state/schema.ts`. A `plan` value contains its header fields and optional shopping metadata (`confirmedAt`, `skippedIncompleteMealIds`, `partial`); slots, shopping items, and repair revisions are separate records with `planId` and zero-based `position` beside `value`. Shopping item values require a stable `id`. The API loads changed records, direct targets, affected plans' slots, and a recipe's indexed meal owner at one revision. It validates changed references without traversing unrelated recovery or correction history. Indexed SQL existence checks cover other incoming dependencies without returning retained dependent history. It removes the V4 whole-file caps on meals, recipes, plans, leftover lots, outcomes, plan repair revisions, and shopping items. Per-record shape limits remain.

`GET /api/records?householdId=<uuid>&kind=<kind>&limit=100` returns `{revision,records,nextCursor}`. Limit is 1–100. Continue with `revision=<returned revision>&after=<nextCursor>` until `nextCursor` is null. A changed household revision returns 409; restart from the first page. `id=<record ID>` looks up one record and returns `{revision,record}` or 404, under the same revision check. Records have `seq`, `kind`, `id`, `planId`, `position`, and `value`.

`POST /api/records` accepts `{householdId,expectedRevision,idempotencyKey,changes}`. Each of 1–100 changes is `{kind,id,value}` plus `planId` and `position` for a plan child. The server validates the changed records and affected references at `expectedRevision`, then one SQL transaction checks live membership and CAS before applying all changes. Success returns `{revision}`. The same key, actor, operation, and payload digest returns the original revision, even after another write; reuse with different payload returns 409. A different actor may use the same key.

There is no hard-delete operation. Outcomes and repair revisions are append-only. Confirmed shopping metadata and items are fixed once recorded. A confirmed slot selection change requires a repair revision in the same changeset. Completed slots retain dinner-ready evidence; an explicit takeout correction must append a takeout revision and, where feedback exists, a corrected outcome. Leftover lots retain their source evidence and may be deactivated. Inactive or corrected records stay as records.

An existing confirmed slot keeps its date. A planned leftover target requires an earlier cooking source slot in the same plan, the same meal, and that meal's explicit `plannedLeftoverDinner` flag. A leftover consumer cannot itself become a planned source. One planned target may reserve a source; one slot across the household may consume an actual leftover lot. A CAS changeset can release one reservation and assign it to another slot atomically. Indexed SQL guards check both reservations again inside the write transaction.

Newly confirmed plans and changed selections in confirmed plans must use an active, safe meal. Selected recipes must belong to the meal and must not use an unavailable shopping ingredient. Hands-off dates require a selected slow-cooker recipe or a valid linked leftover. Constrained dates require at most 30 minutes of effective active effort; unknown effort fails. The effective effort is the average of defined minutes from the latest uncorrected cooking outcomes for the same meal and selected recipe (or name-only meal). Leftover servings and outcomes on leftover-consumer slots do not contribute; without qualifying outcomes, the selected recipe's `prepMinutes` is used. Existing plans made ineligible by later settings or meal edits remain writable pending repair. The server checks these rules on confirmation or repair selection, at the expected revision.

Indexed private projections store current effort count/sum and normalized unavailable shopping lines. Outcome append/correction and shopping item creation update them in the CAS transaction; history reads stay bounded. Any future import or restore path (TREK-34) must build both projections and record references from the imported snapshot before publishing its household revision. The import must preserve only latest uncorrected qualifying effort contributions, including name-only outcomes and leftover-consumer exclusion.

Records are limited to 32 KiB each and a request to 256 KiB. Errors are JSON `{error}` with 400 for malformed/schema/reference/safety failures, 401 for missing or invalid JWT, 403 for unverified user or absent membership, 404 for an absent ID lookup, 409 for stale page/write or idempotency-key conflict, 413 for byte limits, and 500 for backend failures. No response is cached.
